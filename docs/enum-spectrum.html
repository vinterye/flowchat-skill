7. 拓扑全集

按 SKILL.md routing contract 手绘。画的是按规则应有的走向，不是渲染器当前输出 —— 因为其中一部分渲染器输出本身就是错的（见第 8 节）。

1. 对齐端口保持直线

两端都在对面的边界中点、中心同行 → 一条直线，不许为了「好看」加折点。Harness 对这种情况有 straight-aligned 断言。

2. 斜向 · 横向为主

中心连线横向分量占优：从 facing side（right/left）出线，先在空白走廊里折一次，再从目标的水平对面侧进入。

3. 斜向 · 纵向为主

纵向分量占优：从 bottom/top 出线，进入目标的竖直对面侧。目的是防止斜向边「直接从错的那一侧的边界穿出去」。

4. 1→N 扇出 · 横向组 right / left

同一 fanout_group，source_side=right + target_side=left。渲染器产出：一根共享 trunk + 一条分流走廊 + 各目标分支。

5. 1→N · 横向组镜像 left / right

mirrored sides 受支持。实测：方向能统一，但源不居中（§8）。

6. 1→N 扇出 · 纵向组 bottom / top

source_side=bottom + target_side=top，目标沿扇出轴均匀分布。

7. 1→N · 纵向组镜像 top / bottom

向上的镜像组。实测：当前直接崩溃（§8）。

8. N→1 汇合 fanin_group

多条入边先并到一条 merge corridor，再一起进入目标的边界端口。

9. 同侧混合进出 · 分别占用不同车道

同一条边上的入口与出口要各自预留不同编号车道。实测出线占 [1,2]、入线占 [3,2]，lane-2 被两边共用 —— 这就是 3 入 3 出会崩的原因（§8）。

10. centered-flow · 1→2：源对齐目标跨度中点

graph layout.mode="centered-flow"。它会改写你输入的目标坐标（§8）。

11. centered-flow · 1→N：源对齐中间那个目标，目标等距

graph layout.mode="centered-flow"。它会改写你输入的目标坐标（§8）。

12. 显式交叉 crossing: true

intentional crossings 必须打标记；渲染器给它 7 5 虚线。效果是：这里的交叠是声明过的，不是画错了。

11. 枚举过程中实测暴露的缺口

上面每张图都是跑真生成器画出来的，这三条是画的过程中撞出来的。

同行连接含菱形 → 生成器直接崩溃
配对 decision（菱形）时崩溃的类型：无。报错 route segment 0 must be axis aligned。
根因：菱形默认 150×106 vs 常规 156×88 → 两端中心必然纵向差 9px；而 _port_point（1123 行）与 _annotate_semantic_ports（977 行）把圆形与菱形排除在语义端口之外，端口点不落在中性对角线上 → 第一段不是轴对齐 → 走廊建不出来 → 退化为两点直连 → 抛异常。这是第二处崩溃出口，和之前「同侧端口 >3 条」走的是同一个 auto_route or [[sx,sy],[tx,ty]] 兜底。
19 种边类型里 18 种视觉上无法区分
SKILL.md 第 54 行说 parallel / handoff / retry / loop / human_review / event / message 「保留拓扑语义」—— 但实测这 7 种连同另外 11 种画出来完全一样（见 §5）：7 个 marker id 共用同一份 M0,0 L4,2 L0,5 Z 实现和同一个 #98a5bd 填充，stroke 也不变色。语义只活在 DOM 类名里，肉眼不可分辨。只有 return 一种自带虚线。
SKILL.md 自身在举例上有矛盾
第 18 行说「roundRect、胶囊、六边形、梯形等节点会按语义端口自动生成正交路径」，第 54 行说「语义端口适用于所有非圆形、非菱形节点」。注册表里实际有 12 种形状，两条规则的覆盖范围不一样，八边形 / 圆柱 / 平行四边形 / 文档形 / 双框 / 条形这 6 种形状属于哪一档，规则里没写。
